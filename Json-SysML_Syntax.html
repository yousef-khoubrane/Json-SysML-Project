How Json-SysML is structured

A Json-SysML file describes a model through its diagram views. Each view contains the elements and relationships shown in that diagram.

Model and diagrams

The root contains name, id, optional metadata and diagrams. Each diagram specifies its diagramType, name, identity and owner.

Collections group the elements shown in the view. Empty optional collections may be omitted.

Definitions and references

id identifies an element definition; idref references an element within the model; originalID preserves an external-resource identifier in supported shapes and may replace id in an external definition. Names are readable labels. A reused definition may contain just its name and existing id.

A predefined type may use {"name":"Real"}. A model-defined type may use {"name":"name of the block","idref":"block_identifier"}.

Ownership and context

owner.path contains qualified names and owner.idPath contains matching identifiers, both separated by ::. Their segment counts and ordering must match.

context identifies the classifier or behavior whose internals are shown. IBD/PAR context may include port IDs; SD context may include a type.

Stereotypes and tagged values

The stereotypes list contains applied stereotypes retained by the converter. A block may carry ["Block"]. Omit stereotypes when none remain; final cleanup removes empty lists. Requirement, FlowSpecification and Unit are removed from their corresponding collections because the collection conveys that role. QuantityKind is retained.

Stereotypes distinguish element roles. PartProperty, ValueProperty, ReferenceProperty and ConstraintProperty share the property shape. ConstraintBlock is a block stereotype; BindingConnector is a connector stereotype.

Requirements store their text and requirement identifier in taggedValues. Traceability relationships may carry Satisfy, Verify or DeriveReqt stereotypes.

Reading the field reference

Presence tells you when to include a field: required, recommended, optional, or conditional on the selected variant. Role identifies its purpose: an identity, a reference, a kind selector (discriminator), or a value.

scalar means string, number or boolean. Type[] is an array of elements; Vertex[][] groups vertices into region arrays. Keys are case sensitive. A field's meaning depends on its container: a property's type is an object; an action's type is a kind name.

Identifiers and connections

Reuse an element's identifier across diagrams and point references to the intended element. Keep owner name and ID paths aligned, and give connectors two endpoints. A repeated definition may contain only name and id; this differs from an idref reference.

Nested elements

Arrays of IDs reference elements; arrays of objects describe them. For example, a property's ports lists IDs, while a block's ports contains port definitions. Properties, sequence fragments and state vertices can contain nested elements.

Using the templates

Select the diagrams to include and name each entry. The JSON preview, copy and download contain the same selected diagrams. Enable optional fields as needed. After copying or downloading, edit the JSON to replace placeholders, add elements, and make identifiers and references consistent.
